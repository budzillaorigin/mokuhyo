**Assessment**

The automated evidence supports the core practice, persistence and rendering workflows. I would prioritize audio failure handling and the validity of learning feedback before expanding the feature set. Natural live speech can improve substantially with a small local speech model and better playback behavior; a frontier response model is not a prerequisite.

This was a Linux headless review, source inspection and existing-test run. I did not audition the production voices, use a physical microphone, run an installed Windows/macOS release, or measure a real conversation with downloaded LLM/STT models. Those assets are absent in this development environment. Missing local clips do not prove that the published installers lack them.

**Prioritized functionality findings**

1. **High: a failed listening playback can consume an allowed play.** [SkillScreen.kt:490](../desktopApp/src/main/kotlin/app/mokuhyo/desktop/ui/exam/SkillScreen.kt#L490) calls `session.audioPlayed` before playback starts, then ignores the result of `runCatching { AudioIO.play(...) }`. A missing/disconnected output device can therefore cost a test play without audible output. The missing-audio panel also offers no explicit test recovery, despite the loader's message saying tests skip the passage. The test pool checks for an audio metadata entry rather than confirming an accessible, decodable clip. These are source-confirmed failure paths; hardware reproduction remains outstanding. **Improve:** preflight the actual audio/output path; distinguish “could not start” from an intentional stop; surface errors and permit retry without penalizing the learner. Replace unusable test items or explicitly invalidate the affected result.

2. **High: interview tests can advance after speech fails, leaving the question hidden.** The [speaking helper](../desktopApp/src/main/kotlin/app/mokuhyo/desktop/ui/speaking/SpeakingScreen.kt#L255) silently accepts null synthesis and discards playback errors. [The interview flow](../desktopApp/src/main/kotlin/app/mokuhyo/desktop/ui/speaking/SpeakingScreen.kt#L340) then asks for an answer, while test mode forbids displaying the question. The start button checks for an LLM, not a working voice. **Improve:** return a structured speech outcome; require working TTS/output before a voice-only test; on failure offer repair/retry or an explicitly labeled text-practice fallback.

3. **High for assessment quality: review and calibration remain incomplete.** A read-only count found **2,373 reading/listening passages and zero marked human-verified**. The [calibration documentation](../docs/MODELS.md) says the available calibration results are fixtures, not instructor-rated samples. Typed interview answers remain available in test mode, and [saving the estimate](../desktopApp/src/main/kotlin/app/mokuhyo/desktop/ui/speaking/SpeakingScreen.kt#L449) writes a fixed confidence of 0.5 with `provisional=false`, without distinguishing typed answers or calibration status. **Improve:** build a human-reviewed starter bank for each language/level; record response modality; separate typed practice from oral-performance trends; carry calibration status through Home, History and PDFs. Keep model judgments visibly provisional until validated.

4. **Medium: “Play test voice” does not test the voice the app normally uses.** [Voice.kt:20](../desktopApp/src/main/kotlin/app/mokuhyo/desktop/Voice.kt#L20) calls `OsVoice.synthesize` directly. Normal app speech uses [Piper followed by OS fallback](../shared/src/jvmMain/kotlin/app/mokuhyo/tts/VoiceService.kt#L79). A machine with working bundled Piper but no supported OS voice can receive a false “No voice” message. **Improve:** use the same language/voice selection and output path everywhere; show the actual engine and voice being tested.

5. **Medium: the microphone picker can omit devices the recorder can handle.** [AudioIO.kt:24](../shared/src/jvmMain/kotlin/app/mokuhyo/speech/AudioIO.kt#L24) lists inputs only if they support 16 kHz mono. Recording itself tries 48 kHz and 44.1 kHz, mono and stereo, before 16 kHz. **Improve:** enumerate against the same supported-format set. This is a code-level compatibility risk; it needs a device exposing only native-rate capture to reproduce.

6. **Medium: quality gates can overstate real-asset coverage.** Several optional integration tests return normally after logging SKIP, so successful test totals alone do not prove synthesis, recognition or dictionary assets worked. The [round-trip checker](../desktopApp/src/main/kotlin/app/mokuhyo/desktop/LangSmoke.kt#L92) rejects an entirely empty run, but skips individual missing clips and can accept a partial set. **Improve:** report expected/present/tested asset counts, require full declared coverage for a release, and use isolated fixtures for the two corpus-dependent Python tests.

The repository's recorded interviewer evaluation also remains below its 90% sensible-turn target on average: Tier B 76%, C/D 87%. These are historical, model-judged results on the owner's machine, not measurements from this QC. Improve topic/state consistency and targeted regression conversations before assuming a larger model will solve the issue.

**Product improvements**

The main navigation, side-by-side practice layout, review queue and daily stand-to provide a useful foundation. I would make these changes before adding another mode:

- Make the first successful session a short guided practice rather than directing a new learner toward a 30-minute test.
- Show per-language readiness: practice text ready, listening clips ready, live voice ready, microphone ready, recognition ready. Explain unavailable actions before starting a session.
- Keep the existing daily stand-to as the main next action, with a brief reason based on recent mistakes.
- In no-model mode, disable unavailable correction modes and adjust adaptive-interview copy to describe scripted practice accurately. The rendered Speaking screen currently offers correction choices while also explaining that corrections require a model.
- Expand visual QA to 1024×700, 150% scaling, keyboard navigation and screen readers on the actual supported desktop OSes. The screenshot harness's fixed 1280×840 frame cannot validate those claims.

**More natural live voices on ordinary laptops**

The response model chooses the words. TTS determines much of the voice's timbre, pronunciation and intonation; buffering and playback determine how conversational it feels. Keep those components independently replaceable.

| Option | Fit for Mokuhyo | Recommendation |
|---|---|---|
| Kokoro-82M through ONNX | Small local TTS candidate. Documented language overlap includes Japanese, Spanish, French, Brazilian Portuguese and Mandarin Chinese. It does not cover all 11 app languages. | First pilot for supported languages. Compare a quantized model with full precision on actual laptops before choosing. |
| VOICEVOX Core | Japanese-specific option already familiar from the project's prerecorded Japanese listening clips; a native C API is available. | Compare with Kokoro for a neutral adult Japanese interviewer voice. Do not assume every character/style suits an interview. |
| Selected Piper voices / compatible downloaded OS voices | Existing low-overhead fallback; coverage and quality vary by language. | Keep for unsupported Kokoro languages and slower hardware. Offer an honest voice preview and per-language selection rather than always assuming Piper is the best installed option. |
| Chatterbox Multilingual | Already used to prepare lesson audio, with a repository exception scoped to build time. | Continue for prerecorded material. It is not my default live-CPU choice for ordinary laptops. |

Sources checked: [Kokoro project](https://github.com/hexgrad/kokoro), [Kokoro ONNX](https://github.com/thewh1teagle/kokoro-onnx), [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx), [VOICEVOX Core](https://github.com/VOICEVOX/voicevox_core). Kokoro ONNX documents approximately 300 MB for the model, approximately 80 MB quantized, and near-real-time operation on an M1; those are project claims, exclude some assets/runtime overhead, and are not benchmarks I ran.

The existing `SpeechEngine` interface is a useful integration boundary. Java/Kotlin interfaces exist in sherpa-onnx, and VOICEVOX offers a native C API, so investigate adapters or a bundled helper process before budgeting for a complete JVM reimplementation. Check the selected language's phonemizer as well as the neural model. Under this repository's rules, GPL components such as eSpeak must retain appropriate process separation; an ONNX model's license does not determine every runtime dependency's license. Bundle the runtime so users do not need to install Python or a separate service.

**Improvements that help even before replacing TTS**

- **Preserve output sample rate.** [PassageAudio.kt:49](../desktopApp/src/main/kotlin/app/mokuhyo/desktop/PassageAudio.kt#L49) converts synthesized passage audio to 16 kHz, and [Chatterbox import](../desktopApp/src/main/kotlin/app/mokuhyo/desktop/ChatterboxJobs.kt#L96) does the same to higher-rate rendered clips. Keep clean playback at the engine's native rate, generally 22.05/24 kHz or higher; create a separate 16 kHz copy for Whisper. This preserves available high-frequency detail; it does not repair unnatural prosody by itself.
- **Use pitch-preserving slow playback.** [AudioIO.kt:135](../shared/src/jvmMain/kotlin/app/mokuhyo/speech/AudioIO.kt#L135) slows speech by lowering playback sample rate. At 0.8× the pitch drops about 3.9 semitones. Use time stretching that preserves pitch for learner controls.
- **Reduce the wait before the first spoken sentence.** The bridge supports streaming, but [LocalLlamaModel.kt:111](../shared/src/commonMain/kotlin/app/mokuhyo/ai/LocalLlamaModel.kt#L111) discards token callbacks and returns the full response; speech is then synthesized as a whole utterance. Queue complete, validated spoken sentences as they become available, synthesize the next while playing the current one, and support immediate interruption. Do not read partial JSON or unvalidated model fields aloud.
- **Improve phrasing and pronunciation.** Use language-aware pauses, pronunciation overrides and careful handling of numbers, dates, names and abbreviations. The current passage renderer inserts the same 600 ms pause after every line. Preserve the existing stable persona-to-voice assignment.
- **Invalidate cached speech after voice upgrades.** The passage cache key includes language and script text/voice labels, but not the actual engine, model version or selected voice ID. Upgrading a voice can otherwise replay the old synthesized clip.
- **Fix long-piece handling in the build-time renderer.** A read-only diagnostic of the existing `chunks()` function returned a 599-character piece when its limit was 220. It groups sentences but does not split one overlong sentence. Add a real clause/length fallback to avoid the documented truncation risk. The Indonesian-to-Malay mapping in that renderer also needs native-speaker evaluation, not an assumption that the languages are interchangeable.

**Suggested sequence and acceptance checks**

1. Resolve the audio failure paths, voice-test mismatch and microphone enumeration mismatch.
2. Improve playback rate handling, cache versioning and sentence delivery using current voices.
3. Pilot Kokoro on two supported languages, plus VOICEVOX if Japanese is a priority; retain fallbacks for the others.
4. Have native speakers compare recordings blind on naturalness, pronunciation and ease of understanding. ASR round-trip accuracy alone is not a naturalness score.
5. Benchmark while the real local LLM and Whisper are active on an 8 GB laptop and a 16 GB laptop, covering Windows and Apple silicon. Record time to first audio, synthesis time/audio duration, CPU, peak RAM, cancellation delay and voice failures. Faster-than-real-time sustained TTS and prompt interruption are acceptance goals, not claims established here.
6. Complete an offline 20-minute conversation and a listening test with device-disconnect/recovery scenarios before calling the speech workflow release-ready.

The main cost is integration, packaging, downloads and evaluation. Local speech engines do not introduce a per-turn frontier API charge. The best first investment is a small, measured voice pilot plus reliability fixes, while keeping the current response model.
